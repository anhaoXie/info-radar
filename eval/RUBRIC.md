# 判定标准（Rubric）：什么叫做对了

> 这份文件比代码重要。
> 代码写错了改一行就行；判据定错了，你会在错误的方向上优化很久，还很自信。

---

## 一、为什么要写成文件

因为"我觉得这次摘要得不错"不是判据，它无法被复用、无法被比较、无法被交给别人。

判据必须满足三个条件：

1. **离散** —— 能明确回答"对"或"错"，不是"挺好"。
2. **可复现** —— 换一个人、换一天，用同样的标准得到同样的结论。
3. **分层** —— 清楚哪些能自动测，哪些必须人看。混在一起，你就得到一个自己也不信的分数。

---

## 二、判据分层

### A. 自动可测（代码测，每次运行都算）

| 指标 | 定义 | 合格线（建议） |
|---|---|---|
| **格式合规率** | `validate()` 无硬伤的比例 | 首轮 ≥ 90%，稳定后应 100% |
| **分类准确率** | `category` == `gold.category` 的比例 | 首轮随便多少，只要有数字 |
| **重要性平均误差** | \|模型打分 − 真值\| 的平均值 | 越小越好，< 1.0 算可用 |
| **延迟** | 单条 P95 | 决定你能不能接受它每天跑 |
| **成本** | 单条均值、单次合计 | 决定你能跑多大批量 |

**首轮不要设合格线。** 基线的作用是当尺子，不是当门槛。先量出来，再决定要不要继续。

### B. 必须人工看（生成审核表，人填）

| 指标 | 定义 | 为什么不能自动测 |
|---|---|---|
| **遗漏率** | 摘要漏掉原文关键点的比例 | "关键点"需要领域判断 |
| **幻觉率** | 摘要含原文未出现信息的比例 | 判定"原文有没有说过"需要读原文 |
| **依据真实性** | 模型声称的 evidence 是否真在原文里 | 可半自动，但最终要人确认 |
| **重要性合理性** | 打分是否符合 `importance_scale` 的文字描述 | 主观标尺，只能人定 |

#### 关于幻觉率：它比准确率重要

分类分错了，你只是分类分错了。
幻觉出现了，你会**相信一件没发生的事**，并据此做决定。

所以判幻觉时，标准要严：

- **改了语气但事实没变** → 不算幻觉（这是摘要的正常工作）
- **补了原文没有的数字、时间、人名、因果** → 算幻觉，哪怕它"很可能对"
- **把推断写成事实**（"这会导致X"而不是"作者认为这会导致X"） → 算幻觉

第三条最隐蔽，也最常见。「很可能对」不构成写作许可 —— 摘要的职责是压缩，不是补全。

### C. 暂不测（明确写下来，避免自己骗自己）

- 摘要的**文风**是否好看
- `so_what` 是否有**洞察力**
- 是否**选对了值得看的文章**（这是选题问题，不是摘要问题）

写下来的意义是：当有人（包括你自己）说"感觉效果一般"时，
你能指出这属于 C 类，它不是当前优化目标。

## 三、标注规则

1. **宁可标"不确定"，也不要猜。**
   猜出来的金标准比没有金标准更坏 —— 它会让你朝着错误方向优化，而且你不会有任何察觉。

2. **用你的判断，不用模型的判断。**
   看着模型的输出去标真值，你会不自觉地认同它。先自己分类，再看模型说了什么。

3. **不确定的样本要单独标记，不要丢掉。**
   ```json
   { "id": "e012", "gold": { "category": null, "ambiguous": true, "note": "同时属于模型与产品" } }
   ```
   这类样本不计入准确率，但它们告诉你：**你的分类体系有问题**（两个类目重叠了）。
   这是分类体系在给你反馈，比准确率更有价值。

4. **样本量：20 条起步。**
   为什么是 20：少到你能在半小时内标完，多到能区分"55%"和"80%"。
   等到流程跑顺了，再靠审核队列自然涨到 100+。

## 四、回归测试（本 Rubric 存在的主要理由）

S3 阶段你会改提示词、换模型、加示例。每次改动之后：

```
固定评估集 + 固定判据  →  重跑  →  比较数字  →  留或回退
```

**「比较数字」这一步工具会替你做。** `run.cmd eval` 跑完会自动和上一次**可比**的结果对比：

```
  对比基线        out/eval/20261011-214717.json
    分类准确率    55.0% → 70.0%　+15.0%　变好
    格式合规率    100.0% → 100.0%　持平
    重要性误差    0.85 → 0.70　-0.15　变好
    单条成本      0.000310 元 → 0.000420 元　+0.000110 元　变差

  ! 样本只有 20 条，1 条 = 5 个百分点。
    差别看起来不小，但仍然要留一点怀疑。
```

「可比」是严格定义的：**假模型跑的不比、被预算中止的不比、换了任务定义或评估集的不比。**
宁可说"没有可比的基线"，也不给你一个错的对比 —— 一个错的对比会让你改错方向。

**还有那句噪声提醒。** 20 条样本时，1 条就是 5 个百分点；准确率从 55% 涨到 60%，
可能只是换了一条蒙对的。不把这件事说出来，你会为了一个不存在的进步去改提示词，
然后在下一次得到一个不存在的退步 —— **来回震荡，永远收敛不了。**

**纪律：一次只改一个变量。**

同时改提示词和模型，你无法知道是哪个起的作用 —— **那么这次实验白做了**，
甚至更糟：你会把一个有效的改动当成无效的丢掉。

改动记录写进 `eval/CHANGELOG.md`：

```markdown
## 2025-01-15  加入 3 个少样本示例
- 改动：config/task.json 的 prompt.few_shot 加入 3 条
- 模型：glm-5.3-flash（未变）
- 结果：分类准确率 55% -> 80%，单条成本 0.31 分 -> 0.42 分（输入变长）
- 结论：保留。成本上升 35%，换来准确率 +25 个百分点，值得。
```

**没有这行记录，你的所有改进在下个月都归零** —— 因为你不会记得哪次改动起了作用，
于是你不敢再动它，系统就此冻结在某个偶然达到的水平上。
