# 改动记录

> **从 S3 开始，每次改动必须在这里留一行。**
>
> 没有这行记录，你的所有改进在下个月都会归零 ——
> 因为你不会记得哪次改动起了作用，于是你不敢再动它，
> 系统就此冻结在某个偶然达到的水平上。

记录格式（照抄即可）：

```markdown
## YYYY-MM-DD  一句话说清改了什么
- 改动：具体改了哪个文件的哪个字段
- 模型：厂商 / 模型名（如果这次没换模型，写"未变"）
- 结果：分类准确率 X% -> Y%，单条成本 A -> B 分，延迟 C -> D ms
- 结论：保留 / 回退。一句话说明理由（值得用多少成本换多少准确率）
```

纪律：**一次只改一个变量。** 同时改提示词和模型，这次实验就白做了。

---

## 模板（第一次改东西时把它删掉，换成你的真实记录）

## YYYY-MM-DD  示例：加入 3 个少样本示例
- 改动：`config/task.json` 的 `prompt.few_shot` 从 `[]` 改为 3 条同领域示例
- 模型：未变
- 结果：分类准确率 55% -> 80%，单条成本 0.31 分 -> 0.42 分，延迟 2.1s -> 3.4s
- 结论：保留。成本上升 35%，换来准确率 +25 个百分点，值得。

## YYYY-MM-DD  示例：换更便宜的模型（反面案例）
- 改动：模型从 A 换成 B
- 结果：单条成本下降 60%，但分类准确率 80% -> 61%，且格式合规率从 100% 掉到 88%
- 结论：**回退**。省下的钱不足以抵消多出来的 19% 错分类，
  以及格式失败带来的重试开销。教训：便宜的前提是它得先把事做对。
