# 架构蓝图：把"用 AI"拆成六层

> 这份文档是整套系统的根。代码可以重写，目录可以改，这六层不能改。
> 因为它不是关于某个工具的，是关于**一个任务要被机器可靠地完成，到底需要哪些东西同时成立**。

---

## 一、六层结构

自上而下是"决定"，自下而上是"依赖"。

```
                    ┌────────────────────────────────────────────┐
   ⑤ 权限 / 审计层   │ 密钥放哪、能读什么、能写哪、能花多少、留什么痕 │
                    ├────────────────────────────────────────────┤
   ④ 分发 / 审核层   │ 人在哪一步介入、结果去哪、错了谁发现         │
                    ├────────────────────────────────────────────┤
   ③ 工作流层       │ 收集→整理→分析→生成 的编排、失败怎么办       │
                    ├────────────────────────────────────────────┤
   ② 模型层         │ 调哪个模型、怎么调、重试、降级、计量          │
                    ├────────────────────────────────────────────┤
   ① 数据层         │ 从哪来、怎么存、怎么去重、怎么保持新鲜        │
                    ├────────────────────────────────────────────┤
   ⓪ 评估层（地基）  │ 什么叫"做对了"、现在的基线是多少、有没有变差   │
                    └────────────────────────────────────────────┘
      ↑ 地的下面还有一层：ⓞ 任务定义 —— 机器到底替你做什么判断
```

### 每一层唯一要回答的问题

| 层 | 唯一要回答的问题 | 本项目里的实体 | 验收标准 | 最常见失败 |
|---|---|---|---|---|
| ⓞ 任务 | 机器替我做**哪一个判断**？ | `config/task.json` 的提示词与输出结构 | 输出的每个字段都能被人工判定对错 | 任务描述含糊，导致根本无法判断好坏 |
| ⓪ 评估 | 什么叫做对了？基线是多少？ | `eval/eval_set.jsonl`、`eval/RUBRIC.md`、`src/evaluate.py` | 一条命令跑出准确率 / 成本 / 延迟三个数 | 没有基线，于是"感觉变好了" |
| ① 数据 | 料从哪来，是不是干净的？ | `config/sources.json`、`src/collect.py`、`data/` | 同一批数据重跑结果一致，且不重复付费 | 源悄悄失效，静默产出空结果 |
| ② 模型 | 谁来做这个判断，稳不稳？ | `config/providers.json`、`src/llm.py` | 换一家厂商只改配置、不改代码 | 把模型名/价格/接口写死在代码里 |
| ③ 工作流 | 步骤怎么串，哪步坏了怎么办？ | `src/pipeline.py`、`out/logs/` | 中途失败能断点续跑，不重复花钱 | 一步失败整批全丢，或整批重跑 |
| ④ 分发/审核 | 结果去哪，人在哪确认？ | `src/archive.py`、`out/digests/`、审核队列 | 未经确认的产出不会流到"会被当真"的地方 | 直接推送未审核内容，错了三周后才发现 |
| ⑤ 权限/审计 | 敢不敢让它无人值守地跑？ | `.env`、`config/policy.json`、`src/ledger.py` | 断网/超额/密钥失效时**大声失败** | 静默降级：一直在跑，一直在错 |

## 二、为什么正确顺序是反直觉的

绝大多数人的搭建顺序是：

```
找工具 → 搭流程 → 跑起来 → 发现效果不稳 → 怀疑模型 → 换模型 → 还是不稳 → 放弃
```

正确顺序是从地基往上：

```
定义任务 → 定评估标准 → 手工标 20 条真值 → 跑最笨的基线 → 有了数字
   → 接数据源 → 换模型/改提示词，看数字动不动 → 数字动了才算改进
   → 加审核 → 加权限与限额 → 交给定时任务
```

**差别只有一个：有没有一个数字。**

没有数字时，"我换了个提示词"和"我觉得更好了"是同一句话。有数字时，你能说出"分类准确率从 55% 到 80%，单条成本从 0.3 分到 0.4 分"——这时候你才是在**工程**，而不是在**许愿**。

这也是为什么本项目把评估放在第 0 层：它不是一个步骤，它是**其余所有层的地面**。没有地面，上面盖的每一层都无法判断是否歪了。

## 三、三个最容易混淆的边界

搭建时最常犯的错，是把责任放错层。记住这三条分界：

**1. "效果不好"通常不是模型层的问题，是数据层的问题。**
给模型的资料不对、不全、太脏 —— 换再贵的模型也救不回来。上下文工程（给什么资料、什么约束、什么示例）**在责任上属于数据层**，虽然它看起来像是提示词的事。

**2. 重试属于模型层；回退到另一个模型属于工作流层。**
"这个请求超时了，再试一次"是模型层自己能决定的事。
"这个模型连续三次都判不出来，换一个模型试试" —— 这是工作流的决策，因为它涉及成本、涉及换谁的账、涉及结果能不能混用。

**3. 评估层测的是"判断对不对"；分发层管的是"人什么时候看"。**
评估层回答"这批结果里有多少是错的"。
审核层回答"错的那些，在造成损失之前，被谁、在哪一步拦下来"。
前者是**度量**，后者是**风控**。新手常把它们合成一个"人工检查一下"，结果两边都做不好。

## 四、一条数据走完全程（本项目实例）

这是你要做的事：**行业资讯 收集 → 摘要 → 分类 → 存档 / 推送**。

```
① 数据层   从 sources.json 里的源抓取条目 → 按 URL/内容指纹去重 → 原文落 data/raw/
              ↓  （这一步之后，同一篇文章不会再被处理第二次，也就不会重复付费）
③ 工作流层  取出未处理的条目，按批组织
              ↓
② 模型层   带上任务定义（ⓞ）调用模型 → 拿回结构化 JSON
              ↓  每次调用写一行账本：谁、哪个模型、多少 token、多少钱、多少毫秒
⓪ 评估层   校验格式是否合法 → 抽样比对评估集 → 累计准确率
              ↓
④ 分发层   写入 out/digests/日期.md → 需要人工确认的进审核队列
              ↓
⑤ 权限层   全程受 policy.json 约束：限额、白名单、密钥不入日志
```

注意流程里**没有一个环节叫"AI 帮我做一下"**。每个环节都有明确的输入、输出、失败处理和一个可检验的判据。这就是"可编程的认知基础设施"和"更聪明的聊天框"的全部区别。

## 五、检验你是否真的内化了

这套结构的内化标准不是"你能背出六层"，而是：

> **换一个完全不同的任务，你能说出哪几层要重写，哪几层原样不动。**

来自测一下。假设明天你要做的不是"资讯摘要"，而是"每周把销售 Excel 整理成汇报材料"：

| 层 | 要改吗 | 为什么 |
|---|---|---|
| ⓞ 任务 | 全改 | 判断对象从"文章重要性"变成"数据异常与趋势" |
| ⓪ 评估 | **结构不动，内容全换** | 还是要有真值样本和判据，但判据变成数值算得对不对 |
| ① 数据 | 全换 | RSS → Excel 文件；缓存策略从"URL 去重"变成"按周快照" |
| ② 模型 | **几乎不动** | 还是"发消息、收 JSON、记成本"，只换个模型名 |
| ③ 工作流 | 半改 | 步骤数量类似，但"数值计算"这一步不该交给模型，该交给代码 |
| ④ 分发 | 换目标 | Markdown 日报 → PPTX，但"人工确认后才分发"这条原则不变 |
| ⑤ 权限 | **几乎不动** | 限额、白名单、密钥管理、账本与任务无关 |

**能一眼看出 ⓪②⑤ 三层是"可复用的地基"、ⓞ①④ 是"随任务替换的插件"** —— 到这个程度，你才算真的拿到了这套结构，而不是抄了一遍这个项目。

本项目的目录就是照这个划分来的。等你走完全程，回头看目录，看到的应该不再是一堆文件夹，而是这六层。

## 六、这套结构的边界（它不解决什么）

诚实地写下这套方法做不到的事，比写下它能做什么更重要：

- **它不能保证正确。** 它只能保证错误是**可测量、可发现、可回溯**的。准确率 80% 的系统依然每五条错一条——区别在于你**知道**是哪五分之一。
- **它不适用于一次性任务。** 为一年做两次的事搭这套东西是净亏。它成立的隐含前提是：**这个流程你会重复足够多次**，多到"搭建和维护的成本"能被摊薄。
- **它最大的成本不是开发，是维护。** 源会改版、接口会下线、模型会改名、价格会调整。它的真实失败模式不是"搭不起来"，而是"三周前悄悄坏了，你一直在用错的产出"。所以第 ⑤ 层"大声失败"不是可选项。
