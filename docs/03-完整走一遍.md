# 完整走一遍：从零到第一个基线

> 这份文档是**一条命令一条命令地走**，每一步都附上「你应该看到的样子」。
> 这样你能自己判断是走对了，还是卡住了 —— 不需要问我。
>
> 全程估计 40 分钟，其中 30 分钟是标注（唯一不能省的部分）。

工作目录：`C:\Users\谢安豪\Documents\deepseek-harness\default-workspace\info-radar`

所有命令都在这个目录下运行。


## 第 1 步 · 看数据（已经替你取好了）

```cmd
run.cmd sources
```

**你应该看到**（数字会有小波动）：

```
  信息源检查（真实抓取）　可用正文线：200 字

  [OK] 极客公园
       条目 30　【可用 30】　正文 最短1536 中位4549 最长6401　2.7s
       全文源，可用
  ...
  【本轮共可入库 118 篇可用正文】
  够做评估集了。跑：run.cmd collect
```

**这一步要看的是「可用」那两个字后面的数字，不是「条目」。**

- `条目 30　可用 0` = 这个源只给一句话摘要，**一条都用不上**
- `条目 30　可用 30` = 全文源，能用

如果你以后自己加源，加完一定先跑这个命令。一个死掉的源不会报错，
它只是安静地返回零条 —— 然后你会以为"今天没新闻"。

## 第 2 步 · 标注（唯一不能省的部分）

```cmd
run.cmd labels
```

**你应该看到：**

```
  标注进度
  [.......................................]  0%
  总数        20
  已标注      0
  标记不确定  0
  还没填      20
```

现在有**两份**工作纸，次序很重要：

| 文件 | 大小 | 用途 |
|---|---|---|
| **`eval/worksheet-lite.md`** | 10KB | **先看这个。**标题 + 开头一段，20 条一屏扫完 |
| `eval/worksheet.md` | 118KB | 全文版。**只用来查你拿不准的那三五条** |

**先扫速览版，一路填下去。** 大部分条目的分类看标题就够了。
只有你真的犹豫的那几条，再去全文版里搜它的 id。

> **为什么这样设计**
>
> 全文版有 118KB，认真读完要 30–45 分钟。而它恰好卡在整个目标的唯一瓶颈上：
> 没有标注就没有真值，没有真值就没有基线，没有基线后面全部无从谈起。
>
> 但**分类这件事，标题通常就够了**。真正需要全文的是"摘要有没有遗漏/编造"那个判断 ——
> 而那个判断发生在审核队列里（`run.cmd review`），那时候你本来就要读全文。
>
> 所以这里把两个判断拆到两个时间点：**现在只看标题快速分类，以后在审核队列里对着模型输出看全文。**
>
> **一个你愿意做的 5 分钟标注，胜过一个你不会做的 30 分钟标注。**

**看一条，就在 `eval/labels.txt` 里填一行：**

```
<id> | 分类 | 重要性
```

`labels.txt` 里那 20 行的 id 顺序和速览版**完全一致**，所以你可以照着顺序一路填下去，不用来回找。

比如：

```
4511f5752b40 | 产品发布 | 4
3fa8d706f6ab | 模型与技术 | 3
```

### 三条规则

1. **先自己判断，再看模型。**
   你还没跑过模型，所以这条现在天然成立。但**不要**为了省事去跑一次 `eval --stub`
   然后照着填 —— 看着模型的答案标，你得到的是回音，不是标准。

2. **拿不准就写 `?`：**
   ```
   260253a617a4 | ? | ?
   ```
   不确定的样本**不计入准确率**，但它会告诉你一件事：
   **你的分类体系有问题**（两个类目重叠了）。这比准确率更有价值。

3. **重要性不要全给 3。** 那样这一列就没有信息量了，等于没标。

**填完之后：**

```cmd
run.cmd labels
```

应该显示 `100%`、`已标注 20`、`还没填 0`。

```cmd
run.cmd compile
```

**你应该看到：**

```
  已写入 eval/eval_set.jsonl
    可评分样本  20 条
    分类分布    模型与技术 7，产品发布 5，...

  下一步：先填 config/providers.json 的单价，然后
    run.cmd eval -Limit 3
    run.cmd eval
```

### 如果 `compile` 报了这些问题，先处理它们

```
  * 样本只有 8 条。少于 10 条时，准确率的一个样本就值 10 个百分点，数字会非常不可靠。
  * 分类严重不均衡：12/20 条都是「模型与技术」（60%）。
    这种评估集测不出区分度 —— 一个永远回答「模型与技术」的模型也能拿到 60%。
  * 重要性全都是 3。这一列没有信息量了，等于没标。
```

**这三条不是错误，是三个会让你后面那个数字失去意义的陷阱。**
特别是第二条：辛苦标了 20 条、拿到 85% 准确率，感觉很好 ——
直到你意识到"永远猜最多的那一类"能拿到 60%。

## 第 3 步 · 先预览一次（不花钱）

这是你唯一要花钱的那一步，所以先在不花钱的模式下看一遍它长什么样：

```cmd
run.cmd eval --stub
```

**你应该看到：**

```
  --stub：正在用【假模型】跑评估。
  它永远回答「其他」这个分类，所以下面的准确率【没有意义】。
  这个命令验证的是【链路】—— 指标算得对不对、审核表长什么样、结果文件写在哪。

评估集    eval\eval_set.jsonl  共 20 条
任务      news_digest_v1
厂商/模型 stub / stub-model

[  1/20] 4511f5752b40  某公司发布端侧推理框架 VeriLite
        [OK ] 1ms 分类错
...

  本次结果（假模型，仅供预览 ——【不是】你的基线）
  格式合规率      20/20  =  100.0%
  分类准确率      0/20  =  0.0%
  延迟            平均 1ms
```

顺便打开看一眼 `out/eval/<时间戳>-review.md` —— **那才是真正的产出**。
它问你三个自动化测不出来的问题：

- 摘要遗漏了原文的关键点吗？漏了什么
- 摘要里出现了原文没说过的话吗？是哪句
- 它声称的"原文依据"，真的能在原文里找到吗

**准确率错了只是分错类，幻觉错了是你会相信一件没发生的事。** 后者严重得多。

## 第 6 步 · 跑一次生产流程

```cmd
run.cmd pipeline
run.cmd digest
```

`digest` 会生成两份东西：

- `out/digests/<时间戳>.md` —— 日报，**标注着「未审核」**
- `out/review/<时间戳>.txt` —— 审核表，给你填的

打开审核表，格式是：

```
<id> | 收录 | 分类 | 重要性
```

**收录列留空就是通过；分类和重要性已经填了模型的判断，你不改就是认可。**

改完：

```cmd
run.cmd review --apply <时间戳>
```

**你应该看到：**

```
  审核条目   20
  不收录     3
  分类改判   5
  重要性改判 4

  模型分类被你改掉了 5/20 = 25%
  这个数字就是它在真实流量上的准确率 —— 不需要额外跑一次评估。

  回流评估集 17 条新真值
  评估集现在有 37 条样本。
```

> **这是整套系统里唯一一处「它会自己变强」的地方。**
> 你今天人工纠正的每一条，都变成明天的真值样本。
> 评估集从 20 条涨到 200 条时，你对系统的信任就不再是感觉，而是统计。

## 第 7 步 · 交给它自己跑

```cmd
run.cmd daily
```

它按顺序跑 采集 → 处理 → 日报。**默认遇到失败就停** ——
因为一个在失败之后继续产出的流水线，它的产出和有成功时长得一模一样。

然后：

```cmd
run.cmd health
```

```
  任务              连续失败  上次成功        最近结果
  ----------------------------------------------------------------
    collect         0     10-11 21:30   新增 12 条，成功源 6/6
    digest          0     10-11 21:31   日报 20261011-213100.md（12 条可用）
    pipeline        0     10-11 21:31   处理 12/12 条，成功 12

  「今天没新闻」和「流程三周前就死了」在表面上完全一样。
  这张表是你区分它们的唯一依据。
```

**最后一步：把它挂到 Windows 计划任务上，每天跑一次 `run.cmd daily`。**
连续失败 3 次会写 `out/ALERT.md` 并把退出码设成非零。

## 怎么知道你真的内化了

能回答下面这七个问题，说明你拿到的是**这套结构**，而不是这个项目：

1. **你的评估集里有多少条？手工标注和审核回流各多少？**
   → `run.cmd review --stats`

2. **你的模型分类准确率是多少？在什么模型、什么成本下？**
   → `run.cmd status`

3. **把 `config/task.json` 的 `prompt.few_shot` 加三条示例，准确率变成多少？**
   先预测，再验证，然后写一句话结论进 `CHANGELOG.md`。
   （提示：这是"上下文比提示词重要"的实证。你会看到它的提升幅度远大于反复推敲措辞。）

4. **把 `max_body_chars` 从 3000 改成 1000，成本和准确率各会怎么变？**
   **先写下你的预测**，再改、再跑、再对比。预测错了比预测对了更有价值。

5. **你的 6 个源里，哪个最慢？哪个可用率最低？**
   → `run.cmd sources`

6. **如果连续三天没有新内容，`run.cmd health` 会显示什么？**
   → 应该显示「跳过」，**不是**「失败」。为什么这个区分很重要？

7. **换一个完全不同的任务**（比如"每周把销售 Excel 整理成汇报材料"），
   **哪几层要重写、哪几层原样不动？**
   → 回到 [`00-架构蓝图.md`](00-架构蓝图.md) 第五节的表对照。

第 7 题是真正的检验。**能一眼看出哪些是地基、哪些是插件，你才算真的拿到了这套结构。**

## 卡住了怎么办

| 症状 | 先跑这个 |
|---|---|
| 不知道现在该做什么 | `run.cmd status` |
| 报错看不懂 | `run.cmd selftest`（确认不是代码问题） |
| 密钥相关报错 | `run.cmd probe` |
| 源抓不到东西 | `run.cmd sources` |
| 不知道它最近跑得怎么样 | `run.cmd health` |
| 花了多少钱 | `run.cmd ledger` |

**一个通用的排查顺序：**
`selftest` → `mocktest` → `status` → `health` → 具体那一步。
从前到后，是从"代码对不对"到"这一次具体发生了什么"。
