# 学习路线：六个阶段，每阶段一个可检验的产出

> 规则：**每一阶段结束都必须有一个能用眼睛验证的结果。**
> 没有验收标准的阶段不开始。这是我要求你遵守的唯一纪律，也是这套方法和你以前"试试看"的分界线。

---

## 总览

| 阶段 | 建哪一层 | 你会亲手做的事 | 验收（做不到就不进入下一阶段） | 状态 |
|---|---|---|---|---|
| **S0** | ② 模型层 + ⑤ 权限层 | 管密钥、跑通第一次调用、看到账本 | 探测工具列出你账号真实可用的模型；账本里有记录 | ✅ 代码就绪，等 key |
| **S1** | ⓪ 评估层 | 定义判据、标 20 条真值、跑出基线 | 跑出三个数：分类准确率 / 单条成本 / 延迟 | 🔄 标注链路已通 |
| **S2** | ① 数据层 | 接信息源、去重、缓存 | 同一批数据重跑，API 调用次数为 0 | 🔄 抓取已通，**实测推翻了原设计** |
| **S3** | ③ 工作流层 | 串起全流程、按评估数字迭代 | 准确率高于 S1 基线，且能说清是哪个改动带来的 | ✅ 代码就绪，等真实数据 |
| **S4** | ④ 分发 + 审核层 | 归档、人工审核队列、反馈回流 | 审核结果能一键回灌进评估集 | ✅ 代码就绪 |
| **S5** | ⑤ 权限 + 自动化 | 限额、定时、失败告警 | 拔网线 / 改坏密钥 / 超限额时，它大声报错而不是静默 | ⬜ |

> **一条被实测修正的路线说明。**
>
> 严格按这张表，数据层（S2）在评估层（S1）之后。
> 但 S1 要的 20 条真值样本必须来自**真实**文档，所以 S2 的最窄一刀
> ——"取到干净的原文"——被提前实现了。这是对的：
> **分层是责任划分，不是施工顺序。**
>
> 更重要的修正在 [`02-S1-取真实样本与标注.md`](02-S1-取真实样本与标注.md)：
> 实测发现国内 RSS 源只给 7–68 字的一句话摘要，**根本没有正文**；
> 而外文源在你的网络下间歇性 SSL 失败。原设计里"RSS → 摘要 → 评估集"
> 这条路不成立。修法不是换源，是**把"线索来源"和"评估样本来源"解耦**。
>
> 这条修正值得你读一遍，因为它的形状很典型：
> 每一层单独看都对，错在把两个不同目的的流程接到了同一个数据源上。

## S0 · 地基：密钥、模型适配、审计账本

**为什么从这里开始。** 因为这一阶段同时建立两样东西：与模型通话的能力（②），和"每次通话都留痕"的能力（⑤）。先有账本再写业务代码，是这套方法里最反直觉、也最省事的一步——等出了问题再补日志，你会失去出问题那段时间的全部数据。

**你会学到的三个概念：**

1. **Provider 抽象。** 国内几家（智谱、通义、Kimi、豆包）现在都提供 OpenAI 兼容接口。这意味着：一份代码，换 `base_url` + `model` 就能换厂商。**不要为一个模型写一套代码**——模型会换，代码不该跟着重写。

2. **密钥的正确放置。** 密钥只存在于 `.env`（不进 git、不进 `config/`、不进日志）。日志里只允许出现密钥指纹（后 4 位）。缺密钥时必须明确报出"缺哪个变量"，而不是静默返回空串让 API 回一个看不懂的 401。

3. **账本（ledger）。** 一次调用的完整痕迹：什么时候、哪家、哪个模型、多少 token、多少钱、多少毫秒、prompt 的指纹。它是追加写的 JSONL，一行一个事件，**历史行永不修改**。没有它，你后面所有"改好了没有"的判断都无从谈起。

**验收方式：**

```powershell
run.cmd selftest    # 65 项纯逻辑，不碰网络
run.cmd mocktest    # 68 项全链路，本地假服务端
run.cmd probe       # 必须列出你账号真实可用的模型名，而不是配置里我写下的猜测
run.cmd ledger      # 必须能看到调用记录
```

**这一阶段的坑：** 模型名。我写进配置里的模型名只是**猜测**，会过期。探测工具的作用就是用它替换掉猜测——**方案里的这类信息必须能被验证，而不是被相信**。

### 顺带学会的一件事：验证要分层

`selftest` 测纯逻辑（毫秒、不碰网络），`mocktest` 测全链路（本地起一个假的 OpenAI 服务端）。
它们合起来 133 项，**全部跑完不要一分钱、不要你的密钥**。

这不是为了好看。是因为这一层出错的方式都很贵：

| 写错的地方 | 你会付出什么代价 |
|---|---|
| `usage` 字段读错 | 成本统计全错，而你**以为自己很省钱** |
| 重试逻辑写反 | 该重试的不重试，**丢数据** |
| 把 4xx 当成可重试 | 密钥错了却重试三次，白等 |
| 异常信息里带出密钥 | 密钥泄漏进日志 |
| 预算耗尽时抛异常穿透 | **已经跑出来的结果全丢，钱白花** |

最后一条是这一轮真正抓到的东西。`BudgetExceeded` 不是 `LLMError` 的子类，
所以在"预算用尽"时评估脚本会崩掉，并把已完成的结果一起带走。
它平时永远不触发，一触发就同时损失钱和数据 —— 而发现它的成本是零。

> **一条可迁移的原则：能被人为触发的失败，才是能被测试的失败。**
> 真实服务端不会按你的要求失败。假服务端会。
> 所以凡是"出错了怎么办"的代码，都应该有一个能命令它出错的测试。

## S1 · 评估层：先定义"做对了"，再动手做

**这一阶段是整条路线的分水岭。** 大部分人跳过它，然后在后面花十倍时间怀疑模型。

**你会学到的概念：**

1. **判据必须是离散的。** "摘要得不错"无法评估。"分类是否命中预定义标签之一"可以评估。一个任务如果找不到离散判据，说明任务定义得还不够清楚——回到 ⓞ 层重写，而不是硬上。

2. **分层判据：哪些能自动测，哪些必须人工看。**
   - 自动可测：JSON 格式是否合法、分类是否命中、成本、延迟 → 代码测
   - 必须人工：摘要是否遗漏要点、是否出现原文没有的信息（幻觉）、重要性打分是否合理 → 做成**审核表**，人填

   把不可自动测的东西硬塞进自动化，你会得到一个自己也不信的分数。

3. **真值只能人来标，这是苦活，也是唯一的真值来源。** 20 条就够起步。宁可标"不确定"，也不要猜——猜出来的金标准比没有金标准更坏。

4. **基线。** 用最笨的提示词、最便宜的模型跑一遍，记下三个数。这个"笨基线"的价值极高：它是你后面所有改进的比较对象，也是你判断"这个任务值不值得继续做"的依据。

**验收方式：**

```powershell
python src/evaluate.py --set eval/eval_set.jsonl
```
输出三个数。**哪怕准确率只有 40% 也没关系**——有数字的 40% 比"感觉还行"强一百倍。

## S2 · 数据层：让料是干净的，且不重复付费

**你会学到的概念：**

1. **优先结构化源。** RSS / Atom / 官方 API 远远优于抓 HTML。HTML 会改版，改版就静默失效；RSS 是契约。**能拿契约就不要去解析别人的页面。**

2. **两级去重。** URL 去重（同一篇不抓两次）+ 内容指纹去重（换了标题的同一篇内容不重复处理）。第二级才是省钱的那一级。

3. **缓存即账本。** 抓下来的原文落盘，处理状态记在数据里（`processed: true`）。这样重跑不会重复调 API，也就不会重复付费。

4. **新鲜度是有价格的。** 缓存不是越久越好也不是越短越好。策略：源里有发布时间就用它判断，没有就用自己的抓取时间。

**验收方式：** 连续跑两次收集+处理，第二次的 API 调用次数必须是 **0**。这是"缓存真的生效了"的唯一硬证据。

## S3 · 工作流层：串起来，然后**用数字**迭代

> ✅ 代码已就绪：`src/pipeline.py`。现在可以先 `run.cmd pipeline --dry-run` 看它打算做什么，
> 再用 `run.cmd pipeline --stub` 用假模型把整条链路跑一遍 —— 这两个都不需要密钥、不花钱。

**你会学到的概念：**

1. **编排是显式的。** 每一步的输入、输出、失败处理都写在代码里，不藏在某个图形化节点的默认行为里。第 5 层才会做"无人值守"，现在先把"有人看着能跑完"做对。

2. **断点续跑。** 中途挂了，重跑时已完成的不再重做。这是省钱和建立信任的关键——**一个会重复花钱的流程，你不敢多跑，也就不敢改进它。**

   实现上它只有一句话：**每处理完一条就立刻落盘。**
   如果等到整批跑完才写，第 199 条崩溃会让前 198 条的记录一起消失 —— 而它们是花过钱的。

3. **失败隔离。** 一条坏掉不能拖垮整批。三类结局要分开统计，因为它们的处理方式完全不同：

   | 结局 | 含义 | 你该做什么 |
   |---|---|---|
   | `ok` | 正常产出 | 归档 |
   | `format_error` | 模型答了，但结构不合法 | 看提示词，或看任务定义是否有歧义 |
   | `call_failed` | 根本没答上（网络、限流、密钥） | 看错误信息，必要时重试 |

4. **一个必须想清楚的决策：失败的条目要不要标记为已处理？**

   ```
   标记    -> 不会每次重跑都重试，不会静默烧钱。但失败容易被遗忘。
   不标记  -> 失败一定会被重试到成功。但一个永久损坏的条目会每次都在烧钱。
   ```

   这里选**标记 + 记录失败原因**，另外提供 `--retry-failed` 让你主动重试。

   理由：默认重试是错的 —— 它会把"一次偶发失败"变成"每次运行都扣钱"，并且掩盖问题。
   但必须让失败**可见**、让重试**可用**。
   **把"重试"从默认行为变成一次有意识的动作**，是这个设计的全部要点。

5. **迭代纪律（本阶段最重要的东西）。**
   ```
   改一个变量 → 重跑评估 → 记录数字 → 留还是回退
   ```
   一次只改一个：要么改提示词，要么换模型，不要同时改。同时改两个，你就不知道是哪个起的作用——**那么这次实验白做了**。

6. **提示词的作用被高估了。** 在这个阶段你会亲自验证：把同类示例放进上下文（少样本提示），效果提升通常远大于反复推敲措辞。**这是"上下文比提示词重要"这句话的实证。**

**验收方式：**

```powershell
run.cmd pipeline --dry-run      # 只看要处理哪些，不发请求、不要密钥
run.cmd pipeline --stub         # 假模型跑通链路
run.cmd pipeline --stub         # 再跑一次：应该"没有待处理的条目" ← 这就是断点续跑
```

然后才是真跑，并且要能写出这句话：「我改了 ___，准确率从 __ 变成 __，成本从 __ 变成 __。」

> **只读操作不该要求写权限。**
> `--dry-run` 被设计成在任何密钥检查【之前】执行 —— 一个需要密钥才能告诉你
> "我打算做什么"的工具，你只会在已经出错的时候才用它。
> 这条顺序原则值得记住：把所有只读的检查，放在需要凭证的操作前面。

## S4 · 分发与审核：人在哪一步介入

> ✅ 代码已就绪：`src/archive.py`。`run.cmd digest` → 填审核表 → `run.cmd review --apply <时间戳>`。
> 全程不需要密钥。

**你会学到的概念：**

1. **未审核的产出不能流向"会被当真"的地方。** 归档到本地 Markdown 可以随便；发邮件、写进共享文档、推到群里 —— 必须先过审核队列。

   实现上这件事只做了一件事：**让"未审核"这三个字真的出现在文件里**。
   一个只在文档里约定的规矩，会在你最忙的那一周被跳过。

2. **审核队列要极省力。** 一屏一条，格式是给手写的不是给程序读的。

   具体做法：分类和重要性两列**预填模型的判断**，你不改就是认可，只改不对的。
   如果这两列是空的，人就得从头填一遍 —— 审核成本一旦超过自己重做，整个流程就废了，
   而审核一旦没人做，下面的闭环就断了。

3. **闭环：审核结果回流到评估集。** 这是这套系统会**自己变强**的地方——你今天人工纠正的每一条，都变成明天的真值样本。评估集从 20 条涨到 200 条时，你对系统的信任就不再是感觉，而是统计。

   顺带你还白拿了一个数字：

   > 模型分类被你改掉了 1/3 = 33%

   这就是它在**真实流量**上的准确率，不需要额外跑一次评估。
   （前提是你真的每一条都读了。扫一眼就不改的话，这个数字没有意义。）

4. **不要把两个判断混成一个标签。** 「这条值不值得收录」和「这条属于哪个分类」是两件事。
   一条被你标为"不收录"的资讯，它的分类依然可能是对的。
   所以回流时分类标注照收，相关性的判断单独记在 `review_included` 字段里。
   **把它们合成一个标签，是你这一层最容易犯、也最难发现的建模错误** ——
   因为合并之后系统照样能跑，只是它测的东西悄悄变了。

5. **回流必须幂等。** 手滑跑两次不该让评估集里多出一倍的重复样本。
   已存在的 id 会被跳过 —— 这条有测试守着。

**验收方式：**

```powershell
run.cmd digest                              # 生成日报 + 审核表
run.cmd review                              # 看历史产出
#  改 out/review/<时间戳>.txt
run.cmd review --apply <时间戳>              # 生成终版 + 回流评估集
run.cmd review --stats                      # 看评估集来源构成
```

验收标准：从审核表里改一条，它能出现在 `eval/eval_set.jsonl` 里，且带上 `label_origin: "review"`。

## S5 · 权限与自动化：从"能用"到"敢交给它"

**你会学到的概念：**

1. **策略文件化。** 单次运行最多花多少、单日最多花多少、能访问哪些域名、能写哪些目录 —— 全部写在 `config/policy.json` 里，而不是散在代码里。这样"收紧权限"是一次配置修改，不是一次重构。

2. **大声失败 > 静默降级。** 断网了、超额了、密钥失效了 —— 必须有人被通知，而不是安静地跳过。**这是整套系统里唯一一条不允许妥协的原则**：静默失败会同时毁掉产出和你的信任。

3. **定时任务要留最后一次成功的痕迹。** 一张表：任务名、上次成功时间、上次结果摘要、连续失败次数。连续失败 N 次就升级通知。没有这张表，你无法区分"今天没新闻"和"流程三周前就死了"。

**验收方式（三条都要过）：**
- 改坏密钥 → 收到明确报错，指明缺哪个变量
- 拔网线运行 → 明确报网络错误，不产出半成品
- 把限额调到 0 → 拒绝运行并说明原因
