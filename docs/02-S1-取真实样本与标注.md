# S1 · 取真实样本与标注

> 这一章记录的是**实测结果**，不是设想。
> 它是整个项目里第一次"现实修正设计"的地方，也是最有价值的一章。

---

## 一、先看实测数据

S1 要的 20 条真值样本必须来自真实文档。所以先去跑了一遍"从 RSS 抓全文"这条路。

### 第一轮：按"名声"选源 —— 结果几乎全军覆没

第一版启用了 4 个看起来很合理的源（量子位、InfoQ、Google AI Blog、DeepMind）：

```
源           成功 4 / 4
新增入库     2 条
正文过短丢弃 78 条（少于 200 字）
```

**80 条里 78 条被丢弃。** 因为绝大多数 RSS 只给一句话。

| 源 | 它实际给了多少正文 | 能做摘要评估吗 |
|---|---|---|
| 量子位 | 17–18 字 | 不能 |
| InfoQ 中文 | **7 个字** | 不能 |
| Google AI Blog | 22–68 字 | 不能 |
| MIT Technology Review | **6420 – 31508 字** | 能 |

### 关键认识：报"抓到几条"是骗人的

第一版的 `sources` 检查命令只报两件事：抓到几条、多少字节。这两个数字会骗人：

```
量子位      抓到 10 条     ← 看起来挺好
Wired       抓到 50 条     ← 看起来更好
极客公园    抓到 30 条
```

而它们的可用正文长度中位数分别是 **17 字、129 字、4549 字**。前两个源一条都用不上。

> **"条数多"和"能用"是两回事。**
> 你必须量的是【可用正文长度】，不是"抓到几条"。
> 一个只报条数的检查，会让人以为源是好的 —— 这是比"没有检查"更坏的情况。

所以 `run.cmd sources` 后来改成了报这个：

```
  [OK] 极客公园
       条目 30　【可用 30】　正文 最短1536 中位4549 最长6401　2.7s
       全文源，可用
  [OK] Wired
       条目 50　【可用 0】　正文 最短47 中位129 最长196　1.2s
       只有摘要，一条都用不上
```

### 第二轮：量过之后再选 —— 118 篇可用正文

按"可用正文条数"实测 15 个候选源之后：

| 源 | 条目 | 可用 | 正文中位 | 结论 |
|---|---|---|---|---|

| 爱范儿 | 20 | **20** | 3891 字 | 全文源 |
| 钛媒体 | 18 | **18** | 3402 字 | 全文源 |

## 二、核心发现

### 发现 1：大多数 RSS 的职责是"让你决定要不要点进去"，不是"把全文给你"

注意"大多数"这三个字。这正是这一轮最容易搞错的地方 —— 我第一版把它说成了
"RSS 给不出全文"，这个结论**太绝对了**，而且会导致一个错误的行动：
放弃 RSS、去写脆弱的网页抓取。

真相是：**同一个格式，不同源给的东西差 30 倍。**

```
量子位      description 里 17 字
Wired      description 里 129 字
极客公园    content:encoded 里 4549 字
MIT TR     content:encoded 里 6434 字
```

差别不在于"是不是 RSS"，在于**发布者往 `content:encoded` 里放了什么**。
有的放全文，有的什么都不放。

所以正确的结论不是"RSS 不行"，是：
**你得量一下每个源到底给了多少正文，然后按量到的结果选源。**

这一步能解决大部分问题（可用文档 2 → 118），而且完全不用碰网页抓取。
只有当你的领域里确实找不到全文源时，才需要动用"本地投喂"那条后路。

**换多贵的模型都救不回来** —— 数据里没有正文，模型层的天花板由数据层决定。

### 发现 2：源会死，而且死得悄无声息

机器之心和 36氪的订阅地址**返回 HTTP 200**，`content-type` 却是 `text/html` ——
站点改版，订阅地址被重定向到首页。它不报错，只是安静地返回零条。

如果你没写那道 `content-type` 检查，你会得到这样的结论：

> "今天没什么新闻。"

而真相是：**这个源三周前就死了。**

这就是为什么采集器里那条检查是整个数据层最值钱的十行代码：

```python
if "html" in content_type:
    result["error"] = "返回的是 HTML 而不是 XML……通常意味着这个订阅地址已经失效。"
```

### 发现 3：外文源在你的网络下是间歇性可用的

同一个 URL，五分钟前成功、五分钟后 SSL 握手失败（DeepMind、Google、Hugging Face 都出现过）。

这意味着：**任何依赖外文源的设计，都必须把"失败"当作常态而不是异常。**

对应到代码里就是：
- 单源失败 → 报告，继续跑其他源
- 全部失败 → **非零退出**，让定时任务/告警能发现

## 三、架构修正：把这两件事解耦

### 修法有两步，第一步是选源，第二步才是解耦

**第一步：量过之后再选源。** 这一步能解决大部分问题 —— 换掉 4 个纯摘要源、换成 6 个全文源之后，
可用文档从 2 篇变成 118 篇，一行代码都没改。

**第二步（对第一步覆盖不到的情况）：解耦。**

原设计把两件事绑在一起了：

```
❌ 错误的绑定
   RSS 抓取 ──→ 生产线 ──→ 产出
        └─────→ 评估集           ← 问题在这里：评估集被绑死在 RSS 能提供什么上
```

正确的分工是：

```
✅ 解耦
   生产线（信息雷达）：RSS 只负责【发现】
                       标题 + 链接 + 一句话摘要就够了 ——
                       它的任务是帮你决定"这篇要不要看"

   评估集：            需要【你有全文的、你真正关心的】文档
                       它从哪来不重要 —— RSS 全文、网页另存、
                       PDF 转文本、公众号复制粘贴，都行
```

为什么第二步仍然必要：**RSS 是你无法控制的一端。**

你挑到好源不代表永远挑得到。你自己的领域可能根本没有提供全文的 RSS；
你真正想测的那些文档可能来自 PDF、内部报告、付费内容。
把评估集绑在 RSS 上，等于把"我能不能测量我的系统"这件事
交给了一群你不认识的编辑的订阅设置。

**这是这个项目里暴露出的第一个真实架构错误。** 它值得被记住，因为它的形状很典型：
每一层单独看都对，错在**把两个不同目的的流程接到了同一个数据源上**。

## 四、操作流程

### 第 1 步：把文档丢进收件箱

```
data/inbox/
```

支持 `.md` / `.txt` / `.html` / `.json`。以 `_` 开头的文件会被忽略。

**放什么？** 不要放"随便找的 20 篇"。

放**你本来就会认真读的那 20 篇**。

原因很实际：标真值的时候你要读完全文才能判断"模型有没有漏要点、有没有编事实"。
如果文档你自己都不在乎，你不会有耐心认真标；而标得敷衍，整个评估就是假的 ——
你会得到一个数字，然后基于一个假数字做决定。

获取方式随便：RSS 全文、网页另存为、PDF 转文本、复制粘贴，都行。

### 第 2 步：导入

```
run.cmd inbox
```

它会去标签、抽标题、按内容指纹去重，然后和 RSS 抓来的东西用**同一套格式**存进 `data/raw/`。

重复导入同一篇会被跳过 —— 这是内容指纹那一级去重在做的事。

### 第 3 步：抽样

```
run.cmd sample -N 20
```

生成三个文件：

| 文件 | 用途 |
|---|---|
| `eval/worksheet.md` | **先看这个。**每篇正文都在里面，一屏一条，附带分类体系和重要性标准 |
| `eval/labels.txt` | **然后填这个。**格式：`p001 | 分类 | 重要性` |
| `eval/candidates.jsonl` | 机器格式，不要手工编辑 |

抽样不是"取前 20 条"，而是**按来源轮流取**（默认单源上限 6 条）。

为什么要这样：如果 20 条里有 18 条来自量子位，你的评估集测的是
"在量子位的文风下模型表现如何"，而不是"这个任务做得怎么样"。
这叫采样偏差 —— 它会让你的准确率好看或难看，但都与真实使用无关。

### 第 4 步：标注

打开 `worksheet.md` 读，把判断写进 `labels.txt`。

```
p001 | 模型与技术 | 4
p002 | ? | ?
```

- 拿不准就写 `?`，不要猜。不确定的样本不计入准确率，但会告诉你**分类体系有问题**。
- 重要性不要全给 3，那样这一列就没有信息量了。

随时看进度：

```
run.cmd labels
```

### 第 5 步：编译

```
run.cmd compile
```

生成 `eval/eval_set.jsonl` —— 这就是你的评估集。

## 五、编译器会替你检查什么

这一节比"编译"本身重要。`compile` 除了校验格式，还会检查四件
**你自己不会注意到、但会毁掉整个评估**的事：

### 1. 样本太少

> 样本只有 6 条。少于 10 条时，准确率的一个样本就值 10 个百分点，数字会非常不可靠。

### 2. 分类严重不均衡

> 分类严重不均衡：12/20 条都是「模型与技术」（60%）。
> 这种评估集测不出区分度 —— 一个永远回答「模型与技术」的模型也能拿到 60%。

**这是最容易犯、也最隐蔽的错误。** 你辛苦标了 20 条，得到一个 85% 的准确率，
感觉很好 —— 直到你意识到"永远猜最多的那一类"能拿到 60%，
而你的模型只比瞎猜好了 25 个百分点。

### 3. 重要性打分没有区分度

> 重要性全都是 3。这一列没有信息量了，等于没标。

### 4. 正文太短

> 3 条正文短于 300 字，摘要任务在它们上面测不出什么。

## 六、如果你还是想用 RSS

可以，但要接受它的限制，并且**换一个任务定义**：

| 数据里有什么 | 能做的任务 | 不能做的任务 |
|---|---|---|
| 只有标题 | 分类、重要性判断、去重 | 摘要 |
| 标题 + 一句话摘要 | 分类、重要性、**归类与聚类** | 摘要、事实核查 |
| 全文 | 以上全部 + 摘要 + 抽取 | — |

这本身就是一条重要的判断标准：

> **先看你手里有什么数据，再决定让 AI 做什么。**
> 顺序反过来的项目，都会在"效果怎么这么差"的阶段卡住，
> 然后去换模型，然后继续卡住。

## 七、下一步

标注完成后，回到主线：

```
run.cmd eval -Limit 3     # 花几分钱验证链路
run.cmd eval              # 跑出你的基线
```

你会拿到三个数：**格式合规率、分类准确率、单条成本**。把它们记进 `eval/CHANGELOG.md`。

**从这一刻起，你才有资格说"改进了"。** 在这之前，"改进了"和"我感觉好点了"是同一句话。
