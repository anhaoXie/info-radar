# info-radar · 个人 AI 工作系统

把「行业资讯 **收集 → 摘要 → 分类 → 存档 / 推送**」这个每周重复的脑力流程，
交给一套**可测量、可迭代、敢无人值守**的系统。

这不是一个"AI 工具合集"。它是一个**结构**。

结构的用处不在于今天能跑，而在于换任务时你知道：**哪几层要重写，哪几层原样不动。**

## 不用密钥就能做的事

在你还没有填 `.env` 的时候，这套系统已经能做不少事。
**把"不需要密钥的操作"和"需要密钥的操作"分开，是它设计上的一条线索** ——
一个需要密钥才能告诉你"我打算做什么"的工具，你只会在已经出错的时候才用它。

```powershell
run.cmd selftest                  # 离线自检纯逻辑
run.cmd mocktest                  # 全链路自检（本地假服务端）
run.cmd health                    # 任务健康表
run.cmd inbox                     # 导入本地文档
run.cmd sample -N 20              # 抽样本、做标注表
run.cmd compile                   # 编译评估集
run.cmd daily --stub --no-collect # 用假模型跑一遍完整流程
run.cmd digest                    # 看日报和审核表长什么样
run.cmd review                    # 看历史产出
```

`--stub` 会输出明显带 `[假模型]` 标记的内容。这不是多此一举：
**一个看起来像真结果的假结果，比一个明显的错误危险得多。**

> **一个完整的闭环，现在就能走完（不需要密钥）：**
> ```
> 写文档 → inbox → daily --stub --no-collect → 填审核表 → review --apply → health
> ```
> 走完之后，`eval/eval_set.jsonl` 里会多出带 `label_origin: "review"` 的样本。
> 那就是"这套系统会自己变强"的样子。

## 三步跑起来

### 1. 填密钥

把 `.env.example` 复制一份改名成 `.env`，然后**只填你实际拥有的那几行**：

```
ZHIPU_API_KEY=你的key
```

其余的留着不动，程序会自动跳过没有密钥的厂商。

> 为什么是复制成 `.env` 而不是直接改 `.env.example`：模板要跟着仓库走，密钥不能。
> `.gitignore` 已经把 `.env` 排除了。

### 2. 自检 + 探测

```powershell
run.cmd selftest   # 离线自检全部逻辑，不联网不花钱
run.cmd doctor     # 环境自检，不联网
run.cmd probe      # 联网，真实调用一次，并列出你账号可用的模型名
```

`probe` 会告诉你两件事，这两件事都**不能靠猜**：

- 你的 key 到底能不能用（而不是"应该能用"）
- 这家厂商**真实**有哪些模型名（配置里我写的是猜测，会过期）

### 3. 跑基线

把 `probe` 报出来的模型名填进 `config/providers.json` 的 `default_model`，然后：

```powershell
run.cmd eval -Limit 3   # 先跑 3 条，确认链路通
run.cmd eval            # 跑全部，得到基线数字
```

你会拿到三个数：**格式合规率、分类准确率、单条成本**。

**哪怕准确率只有 40% 也没关系。** 有数字的 40% 比"感觉还行"强一百倍 ——
因为从这一刻起，你的每一次改动都能被判断是变好还是变坏。

跑完会生成一张**人工审核表**（`out/eval/*-review.md`），
它问的是自动化测不出来的三件事：**漏了什么、编了什么、打分合不合理**。
花二十分钟填它，你就有了完整的判据。

# ---- 自动化（S5）----

run.cmd daily --stub --no-collect     # 用假模型跑一遍完整流程
run.cmd daily                         # 真正跑一次（要密钥）

# ---- 模型与评估（要联网、要密钥）----

run.cmd probe                         # 探测模型真实可用性

run.cmd eval -Limit 3                 # 快跑三条

### 两层自检，跑在任何要花钱的操作之前

| | 测什么 | 碰网络吗 | 多久 |
|---|---|---|---|
| `selftest` | 纯逻辑：解析、校验、去重、预算、脱敏、日报渲染、审核解析 | 不碰 | 毫秒 |
| `mocktest` | 全链路：真的发 HTTP、真的重试、真的写账本、真的算指标、真的跑流水线 | 只碰 `127.0.0.1` | 几秒 |

`mocktest` 会在本地起一个**假的 OpenAI 服务端**，然后按命令让它失败：
返回 500、返回 429、返回 401、返回不是 JSON 的东西、返回没有 `choices` 的空壳。

**这一步的意义在于：能被人为触发的失败，才是能被测试的失败。**
真实服务端不会按你的要求失败 —— 你想测"429 之后能不能退避重试"，
得先真的把配额打满。而重试逻辑写反的代价是丢数据，
密钥处理写错的代价是泄漏，成本字段读错的代价是你以为自己很省钱。

这三个错误都不便宜，而它们全都不需要花一分钱就能测出来。

> **顺序**：`selftest` → `mocktest` → `probe` → `eval`。
> 先证明代码是对的，再证明密钥是通的，最后才花钱。

## 铁律五条

违反任何一条，这套系统都会在某个你察觉不到的时刻失效。

1. **没有数字的改动不算改动。**
   "我觉得好多了"和"我换了个提示词"是同一句话。改完必须重跑评估。

2. **一次只改一个变量。**
   同时改提示词和模型，你无法知道是哪个起的作用 —— 那么这次实验白做了，
   甚至更糟：你会把一个有效的改动当成无效的丢掉。

3. **宁可大声失败，不要静默降级。**
   源失效了、限额超了、密钥过期了 —— 必须有人被通知，而不是安静地跳过。
   静默失败会同时毁掉产出和你的信任，而且它**不会自己暴露**。

4. **真值只能人标，而且要你先判断再看模型。**
   看着模型输出标真值，你会不自觉地认同它。那样得到的不是标准，是回音。

5. **一次只做一件事，做不完不做下一件。**
   每个阶段都有验收标准。过不了就不进入下一阶段 ——
   否则你会在 S3 遇到一个无法定位的问题，而它其实烂在 S0。

## 这套系统不解决什么

诚实地写下边界，比写下能力更重要：

- **它不保证正确。** 它保证错误是**可测量、可发现、可回溯**的。
  85% 准确率的系统依然每七条错一条 —— 区别在于你**知道**是哪七分之一。
- **它不适合一次性任务。** 为一件事搭这套东西是净亏。
  它成立的隐含前提是：**这个流程你会重复足够多次**，多到搭建和维护成本能被摊薄。
- **它最大的成本是维护，不是开发。** 源会改版、接口会下线、模型会改名。
  真实失败模式不是"搭不起来"，而是"三周前悄悄坏了，你一直在用错的产出"。
  所以第 5 条铁律和第 ⑤ 层不是可选项。
